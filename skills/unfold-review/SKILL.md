# unfold：按需审查

目标是找出影响业务正确性和后续维护的具体问题，不为凑数提出意见。默认中文，用户明确指定其他语言时跟随用户；首次出现的专业术语用普通话解释。

## 先确定依据和范围

- 阅读用户要求、项目规范、受检修改和相关调用方，确认被审查的版本与范围；不能仅凭差异中的几行推断完整业务。
- 从现有代码和文档寻找业务依据，区分确定要求、合理假设与缺失信息。只有关键范围或业务口径仍无法查明时提问。
- 默认不编辑受检代码、不自动修复，也不运行会重写源文件或快照的命令。验证可使用临时目录或外置检查，避免生成物污染受检目录。用户明确要求修复时，再按授权范围执行。

## 按以下顺序检查

1. **业务完整性：**需求是否遗漏或理解错误？多个入口是否遵循同一规则？实现是否只是正常样例能运行？
2. **边界与失败：**关键空值、边界输入、权限和失败情况是否正确处理？是否可能越权、泄漏数据或丢失数据？检查与本次修改相关的实际风险，不扩展成无关安全清单。
3. **结构与重复：**新增结构是否解决现实问题？是否重复实现已有能力、复制同一业务规则或顺带扩大改动？必要的共享函数、权限检查和测试不能因为增加行数而被判为复杂。
4. **维护与验证：**读者能否找到规则位置、调用关系和后续修改入口？交付说明所称的检查是否有证据？缺少交接信息应标为维护建议，不冒充已证实的业务缺陷。

## 用证据报告

- 优先报告影响最大的确定问题。每项包含：**位置（文件与准确行号）、触发条件和实际影响、业务或代码依据、最小修复建议**。
- 对不能复现或依据不足的判断，单列为“待确认”，说明缺少什么证据；不要把猜测写成确定缺陷。
- 没有已证实的问题时明确说出，并说明本次覆盖范围和未验证部分。不要声称已经证明代码没有任何问题。
- 说明实际执行的检查及结果；没有运行测试时直接说明。避免只给主观分数或泛泛而谈的最佳实践。
- 建议修复尽量指向现有规则位置和对应验证入口；只有现有结构确实无法解决问题时才建议新增结构，并说明更简单做法为何不足。

这份 Skill 不自动扩展为全仓库审计，也不创建持续审查模式。
