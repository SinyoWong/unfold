# 业务验收与交接练习

[English](README.en.md) · [项目说明](../README.md)

这些是 **Python 标准库模拟业务练习**，不是生产案例。要求 Python 3.10 或更高版本，无需安装包。检查脚本独立于候选代码；它验证业务行为，不给“易懂度”自动打分。

这里保留首版必要的业务检查和交接练习。使用 Skill 不要求运行这些练习；修改对应业务样本时再检查。理解与协作体验可以从实际任务中反馈：哪里没看懂、哪些判断缺少依据、下次修改是否找得到入口，不必先完成评分表。

## 先检查题目本身

在仓库根目录运行：

```powershell
python -X utf8 evals/check.py --selftest
```

预期显示 `PASS selftest: 8 fixture outcomes verified`：三个起始版本未完成要求，三个参考版本通过，两个故意有缺陷的审查版本被捕获。`PASS ... expected failure detected` 表示题目成功抓到指定缺陷，不表示坏代码业务合格。自检查还验证缺失题目会报错，以及不同工作区能各自导入同名辅助模块，不混用缓存。

| 题目 | 编码任务 | 参考版本 | 审查坏样本 |
| --- | --- | --- | --- |
| `status` | [状态文案](cases/status/task.md) | 只改 `pending` 展示 | 无 |
| `sales` | [退款后销售额](cases/sales/task.md) | 汇总与 CSV 共用退款规则 | 汇总正确，CSV 未减退款 |
| `permissions` | [部门资料详情](cases/permissions/task.md) | 列表与详情共用权限 | 列表正确，详情绕过权限 |

每题 `starter/app.py` 是起始代码，`reference/app.py` 仅供评估者核对，`review-bad/app.py` 是已知缺陷样本。参考结果是一种朴素实现，不要求候选代码逐行一致。

## 编码演练

1. 建立全新的临时工作区，只复制选定题目的 `starter/app.py` 和 `task.md`（英文任务用 `task.en.md`）。不要给执行代理复制 `reference/`、`review-bad/`、本检查脚本或整个 unfold 仓库。
2. 按[安装说明](../README.md#安装与使用)复制 Skill，用新会话发送原始任务；保留请求、过程和最终交付，不修改任务口径来迎合结果。
3. 执行结束后，从工作区外运行验收。例如：

```powershell
python -X utf8 evals/check.py --case sales --workspace C:\Temp\unfold-sales
```

4. 保留退出码及完整输出；成功退出 `0`，业务失败或运行错误退出 `1`。执行代理自行编写的检查也保留，但不能替代外部验收。

`--case` 支持 `status`、`sales`、`permissions`、`sales-handoff`。`--workspace` 指向含 `app.py` 的目录，也允许它导入同目录的辅助模块。每次命令和自检查中的每个样本均使用独立进程，避免模块缓存串到另一工作区。检查会运行候选代码，只应针对自己创建的练习工作区；它不是隔离恶意代码的安全沙箱。

覆盖范围：文案不影响其他状态；退款覆盖空输入、全额退款、取消订单、缺失字段、非法类型、负值、超额退款、大整数及固定随机种子的多组数据；权限覆盖不同角色、缺失部门、跨部门筛选、详情、不存在记录和输入不变。共享规则是否真正集中、解释是否准确，需要查看实际代码和交付说明。

## 按需审查与交接

- 审查时分别复制 `sales`、`permissions` 的正确版本与坏样本到独立工作区，给出业务需求并要求只审查。保存审查前后所有受检文件的 SHA-256（文件内容指纹）并比较，确认没有修改。
- 坏样本必须指出实际遗漏及影响；正确版本不应被误报为业务错误。检查“位置、影响、依据、最小修复建议”是否完整；没有证据的问题应标为待确认。
- 交接使用**实际编码演练的结果与交付说明**，另开独立会话执行 [原金额与退款分列](cases/sales/handoff-task.md)。不要用参考答案冒充上一位代理的产出。
- 交接完成后运行 `--case sales-handoff`，记录代理是否先找到规则位置、澄清问题次数、实际改动和验收结果。缺少上一份交付、无法独立会话或运行失败，都如实记录。
- 本版提供代理接手练习方法；真人独立修改代码与长期维护：**尚未评估**。

## 记录与反馈

普通试用保留任务、实际改动、交付说明、检查输出和遇到的困惑即可。分享时补充日期、模型、客户端和规则版本；无法取得的信息注明未知。实际记录放在本地忽略的 `results/`，教学说明放在 `../examples/`；不要把示范或参考答案标成实测，也不要提交私人对话或凭据。

先确认业务要求与关键边界，再看你是否能理解、判断和继续修改。测试通过不代表理解更准确，代码更短也不能抵消业务失败。原生使用验证按[触发与停用清单](trigger-prompts.md)记录实际读取的 Skill 与行为；未执行的场景保持未验证。
